# 道具选择阶段同步 — 服务器接口需求

> 版本：v1
> 日期：2026-08-17
> 读者：后端实现同学
> 客户端现状：**本文档涉及的全部消息客户端已实现**，服务端按本文档实现后即可联调。
> 前置：请先阅读《联机服务器接口需求.md》（连接/登录/进房/快照为基础链路）。

---

## 1. 流程与角色

```
服务器（权威）                        客户端
   │ ① 进入选择阶段时：抽取道具列表，推送 ItemOfferList ──▶ 触发客户端游戏流程（阶段由服务器开启）
   │ ◀─ ② ItemClaimIntent（玩家点击某道具）────────────│
   │ ── ③ 原样广播 ItemClaimIntentBroadcast ────────────▶ 仅表现（远端图标飞向该道具），不锁道具
   │ ◀─ ④ ItemClaimConfirm（玩家到达+打勾确认）─────────│  ★仲裁点：按收到顺序先到先得
   │ ── ⑤ 广播 ItemClaimResult（成功/被抢）─────────────▶ 客户端据此生效或提示重选
```

服务器侧每房间维护选择状态表（按 round 重置）：

```
selection = { round: 1, claims: { slotIndex -> playerId } }
```

## 2. 各消息处理规则

### ① ItemOfferList（S→C，服务器主动推送）

- **触发时机**：服务器决定进入选择阶段时。客户端的游戏流程由这条消息启动（联机模式下客户端不会自行开局）
- 道具由**服务器**从道具池随机抽取（客户端不再本地随机）
- `item_id` **必须与客户端道具 prefab 名称一致**（客户端按名称映射本地资源）
- `slot_index` 从 0 开始连续编号
- `position` 为场景中道具点位（预留给"角色走到道具位置"玩法，当前面板模式下客户端可忽略）

### ②③ ItemClaimIntent（C→S）→ ItemClaimIntentBroadcast（S→C 广播）

- 收到后**原样广播**给全房间（含发起者），不修改任何状态、不做校验
- 用途：其他端让远端玩家图标飞向目标槽位做视觉表现（"他想要这个"）

### ④ ItemClaimConfirm（C→S，仲裁点）

按收到顺序逐条处理：

```
slot 已被认领        → success=false, code=CONFLICT
该玩家本轮已认领过   → success=false, code=CONFLICT（一人一件）
否则                 → claims[slot]=playerId → success=true, code=OK
```

### ⑤ ItemClaimResult（S→C，广播全房间）

- 广播给**全房间**（不是只回发起者）：成功端生效认领，其他端刷新槽位归属表现，被抢端提示重选
- `player_id` = 本次确认的**发起者**；`success=true` 表示其认领成功，`false` 表示被抢

## 3. proto 位置

`Protos/room/v1/room.proto`：

```proto
message ItemOfferList { room_id, round, repeated ItemOffer offers, server_time_ms }
message ItemOffer { slot_index, item_id, Vector2 position }
message ItemClaimIntent { trace, room_id, player_id, slot_index }
message ItemClaimIntentBroadcast { room_id, player_id, slot_index, server_time_ms }
message ItemClaimConfirm { trace, room_id, player_id, slot_index, client_time_ms }
message ItemClaimResult { room_id, slot_index, item_id, player_id(发起者), success, code(OK/CONFLICT), server_time_ms }
```

gateway envelope 字段号：
- 客户端上行：`item_claim_intent = 23`、`item_claim_confirm = 24`
- 服务器下行：`item_offer_list = 27`、`item_claim_intent_broadcast = 28`、`item_claim_result = 29`

## 4. 游戏阶段切换同步（GamePhaseSync）

**联机模式下客户端不再本地自动切换阶段**（倒计时、选完提前结束等本地条件全部屏蔽），所有阶段切换由服务器广播 `GamePhaseSync` 统一驱动。

### 4.1 消息定义

```proto
enum GamePhaseKind {
  GAME_PHASE_KIND_UNSPECIFIED = 0;
  GAME_PHASE_KIND_PROP_SELECTION = 1;   // 道具选择阶段
  GAME_PHASE_KIND_PROP_PLACEMENT = 2;   // 道具布置阶段
  GAME_PHASE_KIND_PLAYING = 3;          // 跑动/游玩阶段
  GAME_PHASE_KIND_ROUND_SETTLEMENT = 4; // 单轮结算
  GAME_PHASE_KIND_FINAL_SETTLEMENT = 5; // 最终结算
}

message GamePhaseSync {
  string room_id = 1;
  GamePhaseKind phase = 2;
  int32 round = 3;              // 当前轮次（从 1 开始）
  int64 server_time_ms = 4;
}
```

gateway envelope：`game_phase_sync = 30`（服务器下行，广播全房间）。

### 4.2 服务器推进时序（每轮）

```
① 广播 GamePhaseSync{PROP_SELECTION, round=N}     → 各端进入选择阶段
② 广播 ItemOfferList{round=N, offers=[...]}       → 各端收到发牌，展示候选道具
   （①②顺序不限，客户端两边都有缓存兜底；建议先发 ①）
③ 期间处理 ItemClaimIntent / ItemClaimConfirm（见第 2 节）
④ 全员选完或服务器超时（建议 15s）→ 广播 GamePhaseSync{PROP_PLACEMENT}
⑤ 布置阶段超时或全员确认 → 广播 GamePhaseSync{PLAYING}
⑥ 本轮结束 → 广播 GamePhaseSync{ROUND_SETTLEMENT} → 回到 ① 进入下一轮
⑦ 最后一轮 → 广播 GamePhaseSync{FINAL_SETTLEMENT}
```

### 4.3 客户端行为约定

- 收到 `GamePhaseSync` 即进入对应阶段；**重复收到同一阶段会忽略**（幂等）
- 阶段切换由服务器全权决定：本地玩家提前选完**不会**提前切阶段，等服务器指令
- `ItemOfferList` 的 `round` 应与 `GamePhaseSync` 的 `round` 一致

### 4.4 选择阶段结束条件（服务器侧）

满足任一即推进到布置阶段：
- 全员都已认领（claims 数 == 房间在线人数）
- 选择阶段计时到期（建议 15s，超时未选者放弃，放置阶段回退为随机发放）

## 5. 道具摆放阶段同步

### 5.1 流程

```
客户端A                          服务器                       客户端B
   │ 拖拽道具中                     │                             │
   │── ItemPlaceState(10Hz) ──────▶│── ItemPlaceStateBroadcast ─▶│ B端显示A的虚化道具跟随
   │                               │                             │
   │ 点屏幕上方打勾按钮              │                             │
   │── ItemPlaceConfirm ──────────▶│ ★仲裁：cells 与已占用格冲突？ │
   │   {item_id, anchor, cells[]}  │   先到先得                  │
   │◀─ ItemPlaceResult ────────────┤────────────广播────────────▶│
   │ success=true → 本地锁定摆放    │ 占用表登记 cells            │ 生成A的实体道具+标记占用
```

### 5.2 服务器侧数据结构（每房间，每轮布置阶段重置或跨轮保留按玩法定）

```
placement = {
  occupied: Set<"x,y">,          // 已被占用的格子
  placements: [ { player_id, item_id, anchor, rotated, cells } ]
}
```

### 5.3 各消息处理规则

**ItemPlaceState（C→S，约 10Hz）→ ItemPlaceStateBroadcast（S→C 广播）**
- 收到后**原样广播**（含发起者），不校验、不存状态，纯表现
- `position` 为世界坐标、`rotated` 为朝向；`item_id` 变化时表示玩家换了道具（如传送门第二段）

**ItemPlaceConfirm（C→S，仲裁点）**
```
按收到顺序逐条处理：
  cells 中任一格已在 occupied 中 → success=false, code=CONFLICT
  该玩家本轮已确认过该 item_id（防重）→ success=false, code=CONFLICT
  否则 → occupied ∪= cells → 记录 placement → success=true, code=OK
```

**ItemPlaceResult（S→C，广播全房间）**
- `player_id` = 发起者；成功时各端把 `cells` 标记为占用并生成该玩家的实体道具
- 失败只通知发起者调整位置（其他端忽略）

### 5.4 proto 位置

`Protos/room/v1/room.proto`：`GridCell / ItemPlaceState / ItemPlaceStateBroadcast / ItemPlaceConfirm / ItemPlaceResult`。
gateway envelope：上行 `item_place_state = 25`、`item_place_confirm = 26`；下行 `item_place_state_broadcast = 31`、`item_place_result = 32`。

### 5.5 与阶段切换的衔接

- 布置阶段由 `GamePhaseSync{PROP_PLACEMENT}` 开启（见第 4 节）
- 全员确认完毕或超时后，服务器广播 `GamePhaseSync{PLAYING}` 推进
- 格子占用是否跨轮保留由玩法决定：保留则 `occupied` 不随 round 重置；拆除类道具（不占格）不会出现在 cells 仲裁中（客户端会发送空 cells 或跳过，建议服务器对空 cells 直接判成功）

## 6. 通关/出局裁决与结算汇总

### 6.1 流程

```
游玩阶段（PLAYING）
客户端A                          服务器                         客户端B
   │ 到达终点/死亡                  │                              │
   │── PlayerOutReport ───────────▶│ ★裁决：记录出局状态           │
   │  {out_type: FINISHED/DEAD}    │   通关按收到顺序分配名次        │
   │◀─ PlayerOutBroadcast ─────────┤─────────────广播────────────▶│
   │  {player_id, finish_rank}     │                              │
   │                               │ 全员出局（FINISHED+DEAD=全员）  │
   │◀─ GamePhaseSync{ROUND_SETTLEMENT, round=N} ──────────────────▶│
   │                               │                              │
   │ 本地结算本轮得分后             │                              │
   │── RoundScoreReport ──────────▶│ 汇总本轮所有玩家得分            │
   │  {round, score}               │ 累计总分，排名                 │
   │                               │ 有人≥100分？                  │
   │◀─ Settlement ─────────────────┤─────────────广播────────────▶│
   │  {winner, results[rank,...]}  │                              │
   │                               │ 广播 GamePhaseSync：           │
   │                               │  ≥100 → FINAL_SETTLEMENT     │
   │                               │  <100 → PROP_SELECTION(round+1)│
```

### 6.2 服务器侧数据结构（每房间）

```
roundState = {
  round: 1,
  outPlayers: { playerId -> { type: FINISHED/DEAD, finishRank } },
  nextFinishRank: 1,              // 下一个通关名次
  roundScores: { playerId -> score },   // 本轮得分（RoundScoreReport 汇总）
  totalScores: { playerId -> score },   // 跨轮累计
}
```

### 6.3 各消息处理规则

**PlayerOutReport（C→S）→ PlayerOutBroadcast（S→C 广播）**
- `FINISHED`：分配 `finish_rank = nextFinishRank++`，广播；`DEAD`：`finish_rank=0`，广播
- 同一玩家重复上报直接忽略（客户端每轮只报一次，但需幂等防护）
- **全员出局判定**：`outPlayers` 数量 == 房间在线玩家数 → 广播 `GamePhaseSync{ROUND_SETTLEMENT, round}`，重置 `nextFinishRank`、清空 `roundScores`
- 超时兜底：建议游玩阶段服务器计时（如 120s），超时未出局者按 DEAD 处理

**RoundScoreReport（C→S）**
- 客户端收到 ROUND_SETTLEMENT 并完成本地结算后上报；服务器按 `playerId` 记入 `roundScores`，并累加 `totalScores`
- 收齐全员（或超时 3~5s 兜底，缺者按 0 分）后：计算本轮排名 → 广播 `Settlement`
- 之后广播下一阶段：任一玩家 `totalScores ≥ 100` → `FINAL_SETTLEMENT`；否则 `PROP_SELECTION{round+1}` + 新 `ItemOfferList`，重置出局记录

**Settlement（S→C 广播）**：复用既有消息
```
winner_player_id: 当前总分第一名（最终结算时为胜者；轮结算时可为空）
results[]: { player_id, rank, mmr_delta, coin_delta }  // rank 按 totalScores 排；
             mmr_delta/coin_delta 暂无规则可填 0
```

### 6.4 proto 位置

`room.proto`：`PlayerOutType / PlayerOutReport / PlayerOutBroadcast / RoundScoreReport`。
envelope：上行 `player_out_report = 27`、`round_score_report = 28`；下行 `player_out_broadcast = 33`（Settlement 复用已有的 `settlement = 19`）。

### 6.5 客户端行为约定（已实现）

- 本地通关/死亡表现仍即时生效（不等服务器），`PlayerOutReport` 由 `PlayerOutReporter` 自动上报
- `PlayerOutBroadcast` 的名次是权威通关顺序（客户端本地按到达顺序的排名仅作参考）
- 联机模式本地不自动结算：收到 `ROUND_SETTLEMENT` 后客户端先 `SettleCurrentRound()` 再上报得分，结算 UI 展示本地计算结果，服务器 `Settlement` 为权威排名

## 7. 瞬时事件 / 拾取裁决 / 道具生命周期 / 玩家颜色

### 7.1 玩家颜色（color_index）

- `RoomPlayerState` 新增 `color_index = 9`：服务器**按进房顺序从 0 递增分配**，客户端查本地色板（红/蓝/绿/黄/紫/橙/青/粉，超出循环）
- 进房响应与快照的每个 `RoomPlayerState` 都要带上，客户端据此设置化身颜色、选择阶段认领标记、光标颜色
- 断线重连的玩家应保留原色号

### 7.2 PlayerEvent（一次性表现事件）

`C→S: player_event = 29` → `S→C 广播: player_event_broadcast = 34`

```proto
enum PlayerEventType { JUMP=1; HIT=2; PICKUP=3; DIE=4; }
```
- 服务器**原样广播**（含发起者），不校验不存状态
- 客户端自己发出的事件本地已表现，收到广播时跳过自己；其他端在远端化身位置播音效/特效

### 7.3 PickupClaim（收集物拾取裁决）

`C→S: pickup_claim = 30` → `S→C 广播: pickup_claim_broadcast = 35`

- `pickup_id` 约定：关卡金币 `"coin_{anchorX}_{anchorY}"`；道具生成的收集物 `"{itemId}_{anchorX}_{anchorY}_{序号}"`
- 服务器维护 `claimedPickups: Set<string>`：**同一 pickup_id 只广播第一次**，后续重复请求丢弃
- 各端收到广播后移除对应收集物；拾取归属（`player_id`）记入结算数据（金币加分）

### 7.4 ItemStateEvent（道具生命周期）

`C→S: item_state_event = 31` → `S→C 广播: item_state_event_broadcast = 36`

- `item_instance_id` 约定：`"{itemId}_{anchorX}_{anchorY}"`（摆放仲裁结果可推导，各端一致）
- `state_type`：`TRIGGERED=1`（炸弹引爆/闹钟响起）、`DESTROYED=2`（销毁/被拆除）
- 服务器**原样广播**，不存状态。计时由各端本地推演（摆放确认即计时），网络只同步触发/销毁瞬间
- 由**道具所有者端**上报；收到 `DESTROYED` 的端移除对应道具并释放其占据格子

## 8. 注意事项

- **服务端需用最新 proto 重新生成代码**（`Tools/gen_proto.bat` 对应 Go 生成），新消息按 envelope oneof 字段路由
- 选择阶段结束后（全员选完或服务器超时），清空 claims 表；下一轮推送新 `ItemOfferList`（round+1），客户端会自动开始新一轮选择
- 断线玩家的已认领道具默认保留；如需释放某个槽位，广播一条该槽位 `success=false` 的 `ItemClaimResult` 即可让各端解锁
- 超时兜底建议：选择阶段服务器侧计时（如 15s），超时未选择的玩家视为放弃，服务器自行推进到下一阶段
