> 版本：v1　日期：2026-08-17　读者：后端实现同学
> **本文档只列需要新增/修改的内容**，已实现的基础链路（Login/进房/心跳/位置快照等）不在此列。

## 一、已有消息的字段新增（修改点）

### 1. `RoomPlayerState`（进房响应/快照中携带）

```proto
int32 color_index = 9;   // 新增：玩家色号，服务器按进房顺序从 0 递增分配
```
- 客户端查本地色板（红/蓝/绿/黄/紫/橙/青/粉），用于化身颜色/认领标记/光标
- 断线重连的玩家应保留原色号

### 2. `TransformState`（客户端状态上报 + 快照转发，需透传）

```proto
int32 player_state = 7;   // 新增：0=存活 1=幽灵 2=已通关
```

- 客户端已在上报这三个字段，服务端缓存并随 `RoomSnapshot` 原样转发即可，无需理解含义

### 3. `RoomSnapshot`（快照新增道具列表，需组装填充）

```proto
repeated PlacedItemState placed_items = 7;   // 新增：房间内已确认摆放的道具

```

## 三、需要服务器做逻辑处理的消息（其余均为纯转发）

### 1. `ItemOfferList` 主动推送（选择阶段发牌）

- 触发：服务器决定进入选择阶段时（此消息触发客户端游戏流程）
- 道具由**服务器**从道具池随机抽取（客户端不再本地随机）
- `item_id` **必须与客户端道具 prefab 名称一致**（客户端按名称映射本地资源）
- `slot_index` 从 0 连续编号

### 2. `ItemClaimConfirm` → `ItemClaimResult`（道具认领仲裁，先到先得）

```
每房间维护：claims = { slotIndex -> playerId }（按轮重置）
按收到顺序处理：
  slot 已被认领        → success=false, code=CONFLICT
  该玩家本轮已认领过   → success=false, code=CONFLICT（一人一件）
  否则                 → claims[slot]=playerId → success=true, code=OK
结果广播全房间；player_id 填发起者。
```

**超时/结束时未选择玩家的兜底分配（服务器主动发放）：**

```
选择阶段结束时（全员选完或超时），对每个未认领的玩家：
  从未被认领的 offers 中随机挑一件分配给该玩家
  claims[slot] = playerId
  广播 ItemClaimResult{
    player_id = 被分配者, slot_index, item_id,
    success = true, code = OK      // 与手动认领完全同构，客户端零区分
  }
分配顺序与客户端展示一致；剩余未分配道具本轮作废。
全部处理完后再推 GamePhaseSync{PROP_PLACEMENT} 进入布置阶段。
```

### 3. `GamePhaseSync` 主动推送（阶段统一切换）

```
enum GamePhaseKind {
  PROP_SELECTION=1; PROP_PLACEMENT=2; PLAYING=3;
  ROUND_SETTLEMENT=4; FINAL_SETTLEMENT=5;
}

message GamePhaseSync {
  room_id, phase, round, server_time_ms,
  int64 phase_end_time_ms = 5;   // ★本阶段结束的服务器时刻（毫秒），0=无倒计时（游玩阶段）
}
```
- **客户端本地阶段切换已全部屏蔽**，一切切换由服务器推送驱动
- **`phase_end_time_ms` 是倒计时对时锚点**：两端都按"该时刻 - 估算的服务器当前时间"显示剩余时间，保证两端倒计时严格一致。服务器推阶段时必须填（无倒计时的游玩阶段填 0）
- 客户端会用 `server_time_ms` 校准对服务器时间的估算，因此每条 GamePhaseSync 的 `server_time_ms` 必须准确填写当前服务器时刻
- 每轮时序：PROP_SELECTION + ItemOfferList →（选择中）→ PROP_PLACEMENT →（布置中）→ PLAYING →（全员出局）→ ROUND_SETTLEMENT → 有人≥100分？FINAL_SETTLEMENT : 下一轮 PROP_SELECTION(round+1)
- 选择阶段结束条件：全员认领 或 服务器超时（建议 15s）
- 游玩阶段结束条件：**仅"全员出局"一条**（不设硬时长上限）。"全员出局"的定义：**每个人都已死亡或已通关**（允许混合，如 A 通关+B 死亡即满足），不是"全员都死"或"全员都通关"
- **跨轮道具保留**：已摆放的道具与格子占用在轮次之间**不重置**，下一轮玩家在已有布局上继续摆放；仅整局结束（FINAL_SETTLEMENT）时才清空
- 全员掉线时保留 120s 等重连，无人回来则解散结算（详见 §三.5 超时兜底）

### 4. `ItemPlaceConfirm` → `ItemPlaceResult`（摆放格子占用仲裁，先到先得）

```
每房间维护：occupied = Set<"x,y">（⚠️ 跨轮保留，仅整局结束时清空）
按收到顺序处理：
  cells 任一格已在 occupied → success=false, code=CONFLICT
  否则 → occupied ∪= cells → success=true, code=OK
空 cells（拆除类道具不占格）→ 直接判成功。
结果广播全房间（成功时各端生成实体并标记占用）。
```

**同时把摆放结果存入房间状态（供快照恢复，见 §三.8）：**
```
placedItems[key] = { player_id, item_id, anchor_cell, rotated }
// key = "itemId_anchorX_anchorY"（与 item_instance_id 同格式）
```

### 5. `PlayerOutReport` → `PlayerOutBroadcast`（出局裁决 + 名次）

```
每轮维护：outPlayers = { playerId -> {type, finishRank} }，nextFinishRank = 1
  FINISHED → finish_rank = nextFinishRank++（名次按收到顺序）
  DEAD     → finish_rank = 0
  重复上报忽略（幂等）。
全员出局（outPlayers 数 == 在线人数，死亡/通关可混合）→ 推 GamePhaseSync{ROUND_SETTLEMENT}。

超时兜底（修正版：游玩阶段不设硬时长上限）：
  仅当"房间内所有玩家掉线"时启动 120s 重连等待：
    · 120s 内有任一玩家重连 → 取消计时，对局继续
    · 120s 仍无人重连 → 解散本局：未出局者按 DEAD 补记后直接结算存档、
      回收房间资源（无需再推 ROUND_SETTLEMENT，无人接收）
  服务器侧维护：room.allDisconnectedAt（全员掉线时刻，有人在线时重置为 null）
  单个玩家掉线不影响对局：其按 DEAD 补记，其余玩家继续。
```

### 6. `RoundScoreReport` → `Settlement`（结算汇总，复用已有下行 19）

```
收齐全员 RoundScoreReport（或超时 3~5s，缺者按 0）：
  roundScores 记录、累加 totalScores → 按 totalScores 排名
广播 Settlement{ winner=总分第一, results[]{player_id, rank, mmr_delta=0, coin_delta=0} }
再推下一阶段：任一 totalScores ≥ 100 → FINAL_SETTLEMENT；否则 PROP_SELECTION(round+1) + 新 ItemOfferList
```

### 7. `PickupClaim` → `PickupClaimBroadcast`（拾取去重）

```
维护 claimedPickups = Set<string>
同一 pickup_id 只广播第一次（先到先得），后续请求丢弃。
pickup_id 约定：金币 "coin_{anchorX}_{anchorY}"
```

### 8. `RoomSnapshot.placed_items`（快照携带已摆放道具 —— 断连恢复/最终一致保证）

**proto 新增：**

```proto
message PlacedItemState {
  string player_id = 1;         // 摆放者
  string item_id = 2;           // 数字代号（与 ItemCatalog 一致）
  GridCell anchor_cell = 3;     // 锚点格子
  bool rotated = 4;
}

message RoomSnapshot {
  ...原有字段...
  repeated PlacedItemState placed_items = 7;   // 新增（字段7）
}
```

**目的**：摆放同步目前只靠 `ItemPlaceResult` 实时广播，断连/迟到的玩家会永久错过。
快照携带全量已摆放道具后，任何消息丢失都能靠下一条快照补回来（客户端按 key + 占用格双重判重，幂等）。

**服务器逻辑：**

```
① ItemPlaceConfirm 仲裁成功 → placedItems["itemId_anchorX_anchorY"] = {player_id, item_id, anchor_cell, rotated}
② 收到 ItemStateEvent{DESTROYED} → delete(placedItems, item_instance_id)   // item_instance_id 与 key 同格式
③ 每次组装 RoomSnapshot → placed_items = placedItems 全部值
④ placedItems 跨轮保留，整局结束（FINAL_SETTLEMENT）才清空（与 occupied 一致）
```

**客户端行为（已实现）**：收快照时遍历 placed_items，跳过自己摆的与已生成的，缺失的自动实例化 + 登记占用。
