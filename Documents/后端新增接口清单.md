## 三、需要服务器做逻辑处理的消息（其余均为纯转发）

### 1. `ItemOfferList` 主动推送（选择阶段发牌）

- 触发：服务器决定进入选择阶段时（此消息触发客户端游戏流程）
- 道具由**服务器**从道具池随机抽取（客户端不再本地随机）
- `item_id` **必须与客户端道具 prefab 名称一致**（客户端按名称映射本地资源）
- `slot_index` 从 0 连续编号

### 2. `ItemClaimConfirm` → `ItemClaimResult`（道具认领仲裁，先到先得）

```
每房间维护：claims = { slotIndex -> playerId }（按轮重置）
按收到顺序处理：
  slot 已被认领        → success=false, code=CONFLICT
  该玩家本轮已认领过   → success=false, code=CONFLICT（一人一件）
  否则                 → claims[slot]=playerId → success=true, code=OK
结果广播全房间；player_id 填发起者。
```

**超时/结束时未选择玩家的兜底分配（服务器主动发放）：**

```
选择阶段结束时（全员选完或超时），对每个未认领的玩家：
  从未被认领的 offers 中随机挑一件分配给该玩家
  claims[slot] = playerId
  广播 ItemClaimResult{
    player_id = 被分配者, slot_index, item_id,
    success = true, code = OK      // 与手动认领完全同构，客户端零区分
  }
分配顺序与客户端展示一致；剩余未分配道具本轮作废。
全部处理完后再推 GamePhaseSync{PROP_PLACEMENT} 进入布置阶段。
```

### 3. `GamePhaseSync` 主动推送（阶段统一切换）

```
enum GamePhaseKind {
  PROP_SELECTION=1; PROP_PLACEMENT=2; PLAYING=3;
  ROUND_SETTLEMENT=4; FINAL_SETTLEMENT=5;
}

message GamePhaseSync {
  room_id, phase, round, server_time_ms,
  int64 phase_end_time_ms = 5;   // ★本阶段结束的服务器时刻（毫秒），0=无倒计时（游玩阶段）
}
```
- **客户端本地阶段切换已全部屏蔽**，一切切换由服务器推送驱动
- **`phase_end_time_ms` 是倒计时对时锚点**：两端都按"该时刻 - 估算的服务器当前时间"显示剩余时间，保证两端倒计时严格一致。服务器推阶段时必须填（无倒计时的游玩阶段填 0）
- 客户端会用 `server_time_ms` 校准对服务器时间的估算，因此每条 GamePhaseSync 的 `server_time_ms` 必须准确填写当前服务器时刻
- 每轮时序：PROP_SELECTION + ItemOfferList →（选择中）→ PROP_PLACEMENT →（布置中）→ PLAYING →（全员出局）→ ROUND_SETTLEMENT → 有人≥100分？FINAL_SETTLEMENT : 下一轮 PROP_SELECTION(round+1)
- 选择阶段结束条件：全员认领 或 服务器超时（建议 15s）
- 游玩阶段结束条件：**仅"全员出局"一条**（不设硬时长上限）。"全员出局"的定义：**每个人都已死亡或已通关**（允许混合，如 A 通关+B 死亡即满足），不是"全员都死"或"全员都通关"
- **跨轮道具保留**：已摆放的道具与格子占用在轮次之间**不重置**，下一轮玩家在已有布局上继续摆放；仅整局结束（FINAL_SETTLEMENT）时才清空
- 全员掉线时保留 120s 等重连，无人回来则解散结算（详见 §三.5 超时兜底）

### 4. `ItemPlaceConfirm` → `ItemPlaceResult`（摆放格子占用仲裁，先到先得）

```
每房间维护：occupied = Set<"x,y">（⚠️ 跨轮保留，仅整局结束时清空）
按收到顺序处理：
  cells 任一格已在 occupied → success=false, code=CONFLICT
  否则 → occupied ∪= cells → success=true, code=OK
空 cells（拆除类道具不占格）→ 直接判成功。
结果广播全房间（成功时各端生成实体并标记占用）。

【新增】allow_overlap（字段 9，附着类道具如黄油块置 true）：
  ① 跳过格子冲突仲裁（直接批准并广播 ItemPlaceResult）
  ② 不把 cells 记入 occupied（该道具不参与后续冲突判定，与客户端不登记占据的口径一致）
  ③ 仍记入 placedItems（供快照恢复；且拆除仲裁 §10.5 的爆破匹配需能命中它——
     爆破匹配必须按 placedItems 各道具的 cells 直接判定，不能仅按 occupied 反查，
     否则会漏掉黄油块这类不占格子的附着物）
```

**同时把摆放结果存入房间状态（供快照恢复，见 §三.8）：**
```
placedItems[key] = { player_id, item_id, anchor_cell, rotated }
// key = "itemId_anchorX_anchorY"（与 item_instance_id 同格式）
```

### 5. `PlayerOutReport` → `PlayerOutBroadcast`（出局裁决 + 名次）

```
每轮维护：outPlayers = { playerId -> {type, finishRank} }，nextFinishRank = 1
  FINISHED → finish_rank = nextFinishRank++（名次按收到顺序）
  DEAD     → finish_rank = 0
  重复上报忽略（幂等）。
全员出局（outPlayers 数 == 在线人数，死亡/通关可混合）→ 推 GamePhaseSync{ROUND_SETTLEMENT}。

超时兜底（修正版：游玩阶段不设硬时长上限）：
  仅当"房间内所有玩家掉线"时启动 120s 重连等待：
    · 120s 内有任一玩家重连 → 取消计时，对局继续
    · 120s 仍无人重连 → 解散本局：未出局者按 DEAD 补记后直接结算存档、
      回收房间资源（无需再推 ROUND_SETTLEMENT，无人接收）
  服务器侧维护：room.allDisconnectedAt（全员掉线时刻，有人在线时重置为 null）
  单个玩家掉线不影响对局：其按 DEAD 补记，其余玩家继续。
```

### 6. `RoundScoreReport` → `Settlement`（结算汇总，复用已有下行 19）

```
收齐全员 RoundScoreReport（或超时 3~5s，缺者按 0）：
  roundScores 记录、累加 totalScores → 按 totalScores 排名
广播 Settlement{ winner=总分第一, results[]{player_id, rank, mmr_delta=0, coin_delta=0} }
再推下一阶段：任一 totalScores ≥ 100 → FINAL_SETTLEMENT；否则 PROP_SELECTION(round+1) + 新 ItemOfferList
```

### 7. `PickupClaim` → `PickupClaimBroadcast`（拾取去重）

```
维护 claimedPickups = Set<string>
同一 pickup_id 只广播第一次（先到先得），后续请求丢弃。
pickup_id 约定：金币 "coin_{anchorX}_{anchorY}"
```

### 8. `TrapKillEvent` → `TrapKillBroadcast`（陷阱击杀计分归属，纯转发）

```proto
message TrapKillEvent {
  trace, room_id, player_id,        // player_id = 受害者（上报端本地玩家）
  string owner_player_id = 4;       // 陷阱放置者
}
message TrapKillBroadcast {
  room_id, player_id,               // 受害者
  string owner_player_id = 3;       // 陷阱放置者
  server_time_ms
}
```

- 触发：本地玩家被**他人摆放的**陷阱击杀时，受害者端上报；自杀与关卡原生陷阱不上报
- 服务器**纯转发**即可，无需理解/存状态
- 各端收到后为 `owner_player_id` 记一次陷阱有效击杀（客户端计分口径：每次 +5、单轮上限 2 次、无人通关则清零），陷阱主所在端据此把 TrapKill 分计入自己的 `RoundScoreReport`

### 9. 随机事件同步（`GamePhaseSync.event_id/random_seed` + `RoomSnapshot.event_triggered/_at_ms`）

```proto
// GamePhaseSync 追加
int32 event_id = 6;      // 本轮随机事件 ID（1~7），进入 PROP_SELECTION 时重新随机下发
int32 random_seed = 7;   // 本轮随机种子（0~5），同一轮不变，事件内部随机过程各端据此推演

// RoomSnapshot 追加
bool event_triggered = 8;         // 本阶段事件是否已触发（PLAYING 20s 内随机时刻置 true）
int64 event_triggered_at_ms = 9;  // 触发时刻（服务器毫秒时间戳，未触发为 0）
```

服务器职责：
- 进入 PROP_SELECTION 时在 `GamePhaseSync` 携带本轮 `event_id` + `random_seed`
- PLAYING 阶段内随机一个时刻（20s 内），到达后在房间状态置 `event_triggered=true` 并回填 `event_triggered_at_ms`，快照随 tick 自动广播，**无需单独消息**
- 进入新阶段时把 `event_triggered` 复位为 false、`event_triggered_at_ms` 清零

客户端行为（已实现）：两端以 `event_triggered_at_ms` 为服务器时钟锚点定时引爆（误差≈对时误差，几十毫秒）；事件内部随机过程（陨石落点序列）用 `random_seed` 确定性推演，两端逐颗一致；伤害只判本地玩家，死亡走既有 `PlayerOutReport` 裁决。

### 10. 服务器统一算分（proto 字段追加 + 结算下发）

**目标**：得分由服务器统一计算，每轮 ROUND_SETTLEMENT 阶段开始时下发每人分数；客户端本地 `RoundScoreReport` 降级为对账日志，展示以服务器数据为准。

**协议变更（纯字段追加）：**

```proto
// PickupClaim 追加：拾取物分值（金币等得分道具，无分值收集物为 0）
int32 score_value = 5;

// SettlementPlayerResult 追加
int32 round_score = 6;   // 本轮得分
int32 total_score = 7;   // 截至本轮累计总分

// Settlement 追加：结算所属轮次；winner 为空 = 单轮结算，非空 = 最终结算
int32 round = 5;
```

**服务器算分输入来源（均来自既有消息，无需新增通道）：**

| 得分项 | 分值 | 数据来源 |
|---|---|---|
| 通关分 | +20 | `PlayerOutReport{out_type=FINISHED}` |
| 第一名 | +10 | 通关裁决的 finish_rank == 1 |
| 独行 | +15 | 本轮通关人数 == 1 |
| 陷阱击杀 | +5/次，单轮上限 2 次 | `TrapKillEvent` 按 `owner_player_id` 计数（**从纯转发改为转发+计数**） |
| 得分道具 | 按 `score_value` 累加 | `PickupClaim.score_value`，玩家 Finished 时计入、死亡清空 |

**硬规则**：本轮无人通关（Finished 数 == 0）→ 全员本轮 0 分。

**下发时机**：每轮进入 ROUND_SETTLEMENT 时下发 `Settlement{round, results[].round_score/total_score}`；有玩家 total_score ≥ 100 时同一消息带 `winner_player_id` 作为最终结算。

**每轮重置**：进入新一轮（PROP_SELECTION）时清零本轮的陷阱计数/拾取分/安静标记。

**客户端适配（已实现）**：服务器分数字段缺省（未实现算分）时，结算面板回退显示本地算分（规则一致）；字段有值时以服务器为准覆盖。本地记分簿已改为跟随服务器 `GamePhaseSync.round` 翻页，`RoundScoreReport.round` 与实际轮次一致；`Settlement` 晚于面板弹出到达时会自动重建记分行刷新。

### 11. `RoomSnapshot.placed_items`（快照携带已摆放道具 —— 断连恢复/最终一致保证）

**proto 新增：**

```proto
message PlacedItemState {
  string player_id = 1;         // 摆放者
  string item_id = 2;           // 数字代号（与 ItemCatalog 一致）
  GridCell anchor_cell = 3;     // 锚点格子
  bool rotated = 4;
}

message RoomSnapshot {
  ...原有字段...
  repeated PlacedItemState placed_items = 7;   // 新增（字段7）
}
```

**目的**：摆放同步目前只靠 `ItemPlaceResult` 实时广播，断连/迟到的玩家会永久错过。
快照携带全量已摆放道具后，任何消息丢失都能靠下一条快照补回来（客户端按 key + 占用格双重判重，幂等）。

**服务器逻辑：**

```
① ItemPlaceConfirm 仲裁成功 → placedItems["itemId_anchorX_anchorY"] = {player_id, item_id, anchor_cell, rotated}
② 收到 ItemStateEvent{DESTROYED} → delete(placedItems, item_instance_id)   // item_instance_id 与 key 同格式
③ 每次组装 RoomSnapshot → placed_items = placedItems 全部值
④ placedItems 跨轮保留，整局结束（FINAL_SETTLEMENT）才清空（与 occupied 一致）
```

**客户端行为（已实现）**：收快照时遍历 placed_items，跳过自己摆的与已生成的，缺失的自动实例化 + 登记占用。

### 12. `ItemDemolishConfirm` 必须计入"摆放完成"（修复：摆完消除道具不切换阶段）

**问题现象**：布置阶段玩家摆放消除类道具并确认后，阶段卡死不切换到 PLAYING。

**原因**：布置阶段推进条件是"全员确认完毕或超时"。普通道具确认走 `ItemPlaceConfirm`（上行 26），服务器能计入"已确认"；消除类道具走专用通道 `ItemDemolishConfirm`（上行 34，爆破范围允许覆盖已占格子，不走格子冲突仲裁），服务器未将其计入确认集合，"全员确认完毕"永远不成立。

**服务器修复（二选一，推荐 ①）：**

```
① 收到 ItemDemolishConfirm → 完成拆除仲裁（广播 ItemDemolishResult）的同时，
   把该玩家计入本轮"已摆放完成"集合（与 ItemPlaceConfirm 成功等效）。
② 兜底：无论哪种确认通道，阶段都应有超时强制推进（phase_end_time_ms 到期必切），
   避免任何一类确认漏计数导致阶段永久卡死。
```

注意：`ItemDemolishConfirm` 走格子冲突仲裁是**错误**的（爆破就是要覆盖已占格子），不要为计入确认而把它并回 `ItemPlaceConfirm` 的仲裁流程，只需复用其"确认计数"。

### 12.5 链式道具确认：`ItemPlaceConfirm.expect_more`（字段 11）— 新增

**问题现象**：传送门是两段式道具（摆完第一段还有第二段），但服务器按确认计数判定"全员确认完毕"——
收到该玩家第一次确认（第一段）即标记其已完成，全员完成后广播 PLAYING 推进阶段，
第二段还没摆阶段就结束了（阶段结束还会清掉未配对的两个门）。

**协议**：`ItemPlaceConfirm` 新增字段：

```proto
// 链式道具（传送门第一段等）置 true：本次确认后同一玩家还有后续确认，
// 服务器"全员确认完毕"计数时不得将本玩家计入已完成，直到收到其无此标记的确认
bool expect_more = 11;
```

**服务器规则**：

```
① 玩家"已完成"的判定从"收到过确认"改为"收到过 expect_more=false 的确认"
② expect_more=true 的确认：照常做格子仲裁 + 记录 placedItems（第一段门要生成），
   但不把该玩家计入"已完成"
③ 同轮同玩家收到 expect_more=false 的确认后，才计入"已完成"
④ 兜底不变：阶段超时（phase_end_time_ms 到期）强制推进，防计数异常卡死
```

**客户端行为（已实现）**：确认时检测当前道具是否带链式后续（Portal.HasChainedItem），
第一段确认自动携带 `expect_more=true`；第二段（无后续）确认不带标记（默认 false）。

### 13. 旋转吐司尺寸同步（`ToastSizeSync` / `ToastSizeBroadcast`，上行 37 / 下行 41）— 新增

**背景**：旋转吐司（itemId=13）每轮尺寸随机（边长 1/2/3 格），各端必须一致。
放置者端本地随机后上传，服务器纯透传广播。

```proto
message ToastSizeSync {           // 客户端 → 服务器
  TraceContext trace = 1;
  string room_id = 2;
  string player_id = 3;           // 上报者（吐司放置者）
  int32 round = 4;                // 生效轮次
  int32 size = 5;                 // 边长格数：1/2/3
}
message ToastSizeBroadcast {      // 服务器 → 全房间
  string room_id = 1;
  string player_id = 2;
  int32 round = 3;
  int32 size = 4;
}
```

**服务器处理逻辑**：

```
① 收到 ToastSizeSync → 原样广播 ToastSizeBroadcast 给全房间（含上报者，客户端跳过自己）
② 【建议】按房间缓存最近一次 {round, size}，断线重连/迟加入端补发
   （不缓存不影响在线各端，仅重连端会看到 prefab 默认尺寸）
③ 一轮内多次上报以最后一条为准（两名玩家同轮都放吐司的竞态场景）
```

**客户端行为（已实现）**：本地确认摆放吐司且本轮尺寸未决定时随机并上传；收到广播后
应用尺寸——更新 CurrentSize 并同步场上全部已存在实例，之后实例化的吐司自动读取。
服务端道具表需同步登记：**itemId=13 = 旋转吐司**（发牌池映射）。
