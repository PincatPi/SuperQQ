# SuperQQ 局内联机 — 服务器接口需求

> 版本：v1（移动同步最小闭环）
> 通信方式：WebSocket 二进制帧 + Protobuf
> 同步模型：**客户端权威 + 服务器纯转发**（服务器不做游戏逻辑，只做缓存与广播）

## 1. 协议文件

- 协议目录：`Protos/`（proto3）
- 统一封装：`Protos/gateway/v1/gateway.proto`
  - 客户端 → 服务器：`ClientEnvelope`（oneof payload，按字段路由）
  - 服务器 → 客户端：`ServerEnvelope`
- 每条消息携带 `seq`（客户端自增）和 `trace`（TraceContext），回包 trace 中需带上 `session_id` / `gateway_id`

## 2. 需要实现的接口清单

| # | 消息 | 方向 | 优先级 | 说明 |
|---|------|------|--------|------|
| 1 | WebSocket `/ws` | - | P0 | 接受连接，分配 session_id |
| 2 | `LoginRequest` → `LoginResponse` | 请求/响应 | P0 | device_id 免注册登录，**分配 player_id** |
| 3 | `JoinRoomRequest` → `JoinRoomResponse` | 请求/响应 | P0 | 进房，房间不存在则自动创建 |
| 4 | `SyncPlayerStateRequest` | 请求（无需响应） | P0 | 覆盖缓存该玩家的 transform |
| 5 | `RoomSnapshot` | **服务器主动推送** | P0 | 向房间全员广播最新状态 |
| 6 | `HeartbeatRequest` → `HeartbeatResponse` | 请求/响应 | P0 | 保活 + 刷新会话活跃时间 |
| 7 | 断线清理 | 内部逻辑 | P1 | 移除离线玩家并广播 |

## 3. 各接口详细逻辑

### 3.1 WebSocket 连接

- 接受连接后生成 `session_id`（UUID 即可）
- 维护连接对象表：`session_id → conn`
- 之后所有回包在 `trace` 中携带 `session_id`、`gateway_id`

### 3.2 登录 LoginRequest

入参：`device_id`（设备唯一标识）、`client_version`

逻辑：
1. 按 `device_id` 查玩家（调试期可用内存 Map）：
   - 已存在 → 返回已有玩家数据
   - 不存在 → 创建新玩家：`player_id` 用自增 ID 或 UUID 前缀（如 `p1001`），`nickname` 随机生成（如 `玩家5842`）
2. 生成 `token`（随机串即可）及过期时间
3. **建立绑定：`session_id ↔ player_id`**，后续该连接的消息以绑定关系认定身份（不信任消息体里的 player_id，防冒充）
4. 返回 `LoginResponse { status: OK, token, player: { player_id, nickname, level, mmr, coins }, expires_at_ms }`

### 3.3 进房 JoinRoomRequest

入参：`room_id`、`player_id`、`gateway_id`、`session_id`

逻辑：
1. 按 session 绑定找到玩家
2. 查房间表，`room_id` 不存在则**自动创建**（phase = `ROOM_PHASE_BATTLE`）
3. 将该玩家加入房间玩家表：
   `players[player_id] = { session_id, playerRef, transform: 空, connected: true }`
4. 返回 `JoinRoomResponse`，**携带完整 Room**（含已在房间所有玩家的 playerRef 和最后缓存的 transform），使晚进房玩家能立即看到先来者

### 3.4 状态上报 SyncPlayerStateRequest（最高频路径，20Hz/人）

入参：`room_id`、`player_id`、`transform: { position, direction, velocity, state_seq, client_time_ms, player_state, facing_left }`

逻辑：
1. 以 session 绑定的 player_id 为准定位玩家
2. 覆盖缓存：`players[player_id].transform = transform`，并填 `server_time_ms`
3. **无需返回 SyncPlayerStateResponse**（客户端不处理）
4. 注意：此路径要极快，不做校验、不写库

### 3.5 房间快照广播 RoomSnapshot（服务器主动推）

触发方式（二选一，建议先 A 后 B）：
- **A. 立即广播**：每处理完一条 SyncPlayerState 就组装快照发给全房间（实现最简单）
- **B. 定时聚合**：每房间 15Hz 定时器，状态有变化（脏标记）才广播（省带宽）

快照内容：
```
RoomSnapshot {
  room_id, tick（自增）, server_time_ms,
  players: [ 房间玩家表完整拷贝：{ player: {player_id, nickname}, hp, energy, score,
           connected, alive, transform（含 player_state / facing_left，原样透传） } ]
}
```
- 通过 `ServerEnvelope.room_snapshot` 发给房间内每个 session（**包括上报者自己**，客户端会自行跳过自己）
- `transform` 必须原样透传客户端上报的全部字段（proto 需与客户端同步重新生成）

### 3.6 心跳 HeartbeatRequest

入参：`client_time_ms`

逻辑：返回 `HeartbeatResponse { server_time_ms: 当前服务器毫秒, client_time_ms: 原样返回 }`，并刷新 session 最后活跃时间。

### 3.7 断线清理（P1）

- WebSocket 断开或超过 15s 无消息 → 从所在房间玩家表移除该玩家（或标 `connected=false`）
- 触发一次快照广播，其他客户端据此移除该玩家化身
- 房间无人后延迟回收房间

## 4. 当前联调状态

- 客户端已完成：自动连接 → 自动登录 → 自动进房 → 20Hz 上报 → 快照接收插值
- **当前卡点：LoginRequest 发出后服务器无响应**（客户端连接正常、无解析错误、无断开）
- 排查建议：在网关加日志确认 ①是否收到该 WebSocket 消息 ②oneof 的 `login` 字段是否识别 ③account 逻辑是否执行 ④响应是否写回正确会话

## 5. 验证方式

客户端运行后 Console 过滤 `[NetWork]`，预期依次出现：
```
连接已建立 → 发送 LoginRequest → 收到 LoginResponse（拿到 player_id）
→ 发送 JoinRoomRequest → 收到 JoinRoomResponse（拿到 roomId + 玩家列表）
→ 开始上报本地玩家状态 → 首个房间快照到达
```
双端各跑一次即可互见对方移动。
