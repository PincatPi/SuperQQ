## 0. 给后端的实现顺序建议（最小闭环优先）

| 批次 | 内容 | 说明 |
|---|---|---|
| **第一批（跑通局外）** | Login 账号密码校验、CreateRoom（记录 owner）、JoinRoom（不存在回 NotFound）、**GetRoom**、SetReady、StartGame | 客户端在等待房间每 2s 轮询 `GetRoom`，**第一版可以不实现任何推送**，状态变更靠轮询同步，流程即可跑通 |
| **第二批（体验优化）** | `RoomUpdated` 推送（成员进出/准备/开局实时广播） | 实现后客户端实时刷新，轮询成为冗余兜底 |
| **第三批（局内）** | SyncPlayerState 缓存、RoomSnapshot 广播、断线清理 | 若之前联调已完成则无需改动 |

## 1. 总体约定

### 1.1 架构模型

- **客户端权威 + 服务器纯转发**：服务器不做游戏逻辑（无碰撞/伤害/胜负判定），只做账号、房间管理、状态缓存与广播。
- 同步模型：每个客户端 30Hz 上报自己的位置/朝向/状态 → 服务器覆盖缓存 → 向房间全员广播快照。

### 1.2 通信方式

- **WebSocket 二进制帧 + Protobuf**，入口 `ws://<host>:<port>/ws`。
- 协议目录：`Protos/`（proto3），统一封装在 `Protos/gateway/v1/gateway.proto`：
  - 客户端 → 服务器：`ClientEnvelope`（oneof payload，按 oneof 字段路由到对应处理器）
  - 服务器 → 客户端：`ServerEnvelope`（同步应答与服务端推送复用同一结构）
- 每条客户端消息带 `seq`（自增）与 `trace`（TraceContext）。**所有服务端回包/推送必须在 `trace` 中携带 `session_id` 和 `gateway_id`**——客户端依赖首个回包 trace 自动捕获这两个值，后续请求会原样带回。
- proto3 兼容性：协议有更新时双方都用最新 `Protos/` 重新生成。**服务端务必用最新 proto**，否则 `owner_player_id`、`ready`、GetRoom 等新字段/新路由全部不生效。

### 1.3 会话与身份绑定

1. 接受 WebSocket 连接后生成 `session_id`（UUID 即可），维护 `session_id → conn` 连接表。
2. 登录成功后**建立 `session_id ↔ player_id` 绑定**，此后该连接的所有请求以绑定关系认定身份，**不信任消息体中的 `player_id`**（防冒充）。
3. 维护会话最后活跃时间，心跳与任意业务消息均可刷新。

### 1.4 通用返回码（common.proto `ResultCode`）

`OK=1`、`BAD_REQUEST=2`（参数错误/状态不允许）、`UNAUTHORIZED=3`（未登录/密码错误）、`FORBIDDEN=4`（无权限，如非房主开局）、`NOT_FOUND=5`（房间不存在）、`CONFLICT=6`（房间码已被占用）、`BUSY=7`（房间已开局）、`INTERNAL_ERROR=8`。

网关级异常（坏包、未知路由）统一回 `ErrorResponse { status, route }`，`route` 为 oneof 字段名（如 `"login"`、`"join_room"`），客户端按 route 分发处理。

## 2. 接口清单

| # | 消息 | 方向 | 优先级 | 说明 |
|---|------|------|--------|------|
| 1 | WebSocket `/ws` | - | P0 | 接受连接，分配 session_id |
| 2 | `LoginRequest` → `LoginResponse` | 请求/响应 | P0 | 账号密码校验；device_id 免注册兜底 |
| 3 | `CreateRoomRequest` → `CreateRoomResponse` | 请求/响应 | P0 | 创建房间（phase=WAITING，记录 owner） |
| 4 | `JoinRoomRequest` → `JoinRoomResponse` | 请求/响应 | P0 | 按房间码进房；不存在回 NOT_FOUND |
| 5 | `GetRoomRequest` → `GetRoomResponse` | 请求/响应 | P0 | **拉取房间全量状态（客户端 2s 轮询）** |
| 6 | `SetReadyRequest` → `SetReadyResponse` | 请求/响应 | P0 | 设置准备状态 |
| 7 | `StartGameRequest` → `StartGameResponse` | 请求/响应 | P0 | 房主开局，全员 ready 校验，phase→BATTLE |
| 8 | `RoomUpdated` | **服务端推送** | P1 | 房间大厅状态实时广播（有轮询兜底，可后做） |
| 9 | `SyncPlayerStateRequest` | 请求（无需响应） | P0 | 对局内 30Hz 状态上报，覆盖缓存 |
| 10 | `RoomSnapshot` | **服务端推送** | P0 | 对局阶段向房间全员广播状态快照 |
| 11 | `HeartbeatRequest` → `HeartbeatResponse` | 请求/响应 | P0 | 保活 + 刷新会话活跃时间 |
| 12 | 断线清理 | 内部逻辑 | P1 | 移除离线玩家并广播 |

## 3. 局外流程接口（登录 → 建房 → 开局）

### 3.1 客户端链路参考

```
Lobby（登录页：手动输入账号密码）→ Hall（大厅：创建/加入房间）→ Room（房间等待：准备/开局）→ Level1（对局）
```

客户端行为：登录页**不再自动登录**，必须用户点击登录按钮、在弹窗输入账号密码后才发送 LoginRequest。

### 3.2 登录 LoginRequest → LoginResponse

**入参**：`device_id`、`client_version`、`username`、`password`（后两个为新增字段）

**逻辑**：
1. `username` 非空 → 走**账号密码校验**：
   - 账号已存在：校验密码。**密码错误回 `UNAUTHORIZED`**，message 如 "账号或密码错误"
   - 账号不存在：**自动注册**（免注册流程），分配 `player_id`（如 `p1001`），`nickname` 可用账号名或随机生成（如 `玩家5842`）
   - 密码存储需加盐哈希，不存明文
2. `username` 为空 → 回退 **device_id 免注册**（兼容旧逻辑）
3. 生成 `token`（随机串）+ `expires_at_ms`
4. 建立 `session_id ↔ player_id` 绑定
5. 返回 `LoginResponse { status: OK, token, player: { player_id, nickname, level, mmr, coins }, expires_at_ms }`

> ⚠️ 当前联调状态：后端旧逻辑不识别 username/password，任意输入都会登录成功（按 device_id 放行）。实现本节后，错误密码才会被拒绝。

### 3.3 创建房间 CreateRoomRequest → CreateRoomResponse

**入参**：`room_id`（客户端生成的 6 位数字房间码）、`mode`、`players`（含创建者 PlayerRef）、`created_at_ms`

**逻辑**：
1. `room_id` 已存在且房间未关闭 → 回 `CONFLICT`（客户端会重新生成房间码再试）
2. 创建房间：`phase = ROOM_PHASE_WAITING`，**`owner_player_id = 创建者 player_id`**（新字段，务必填，客户端靠它判定谁是房主）
3. 将创建者加入玩家表：`players[player_id] = { playerRef, session_id, ready: false, connected: true, transform: 空 }`
4. 玩家已在其他房间 → 先从旧房间移除
5. 返回完整 `Room`（含 `owner_player_id`、玩家列表）

### 3.4 加入房间 JoinRoomRequest → JoinRoomResponse

**入参**：`room_id`、`player_id`、`gateway_id`、`session_id`

**逻辑**：
1. 按 session 绑定定位玩家；未登录回 `UNAUTHORIZED`
2. 房间不存在 → **回 `NOT_FOUND`（不要自动创建）**，客户端向玩家提示"房间不存在，请检查房间码"
3. 房间已开局（BATTLE）→ 回 `BUSY`（message 如 "该房间已开始游戏"）
4. 加入玩家表（`ready: false, connected: true`），玩家已在其他房间先移除
5. （第二批）向房间内其他成员推送 `RoomUpdated { room, reason: "player_joined" }`；**未实现推送时，房主端靠 GetRoom 轮询 2s 内看到新成员**
6. 返回 `JoinRoomResponse` 携带**完整 Room**

### 3.5 拉取房间 GetRoomRequest → GetRoomResponse（新挂载，务必实现）

**入参**：`room_id`

**逻辑**：
1. 房间不存在 → 回 `NOT_FOUND`
2. 返回 `GetRoomResponse { status: OK, room }`，**携带完整 Room**（`owner_player_id`、所有玩家的 playerRef / `ready` / `connected` / `phase`）

> 客户端在房间等待阶段每 2s 轮询此接口，用于同步成员进出、准备状态、开局 phase。**这是第一版"房主看到新人加入"的数据来源**，不实现会导致等待页永远只有进房瞬间的快照。

### 3.6 设置准备 SetReadyRequest → SetReadyResponse

**入参**：`room_id`、`player_id`、`ready`

**逻辑**：
1. 仅 `WAITING` 阶段允许，否则回 `BAD_REQUEST`
2. 更新 `players[player_id].ready = ready`
3. 返回 `SetReadyResponse { status: OK, ready }`
4. （第二批）推送 `RoomUpdated { room, reason: "ready_changed" }`；未实现推送时客户端轮询同步

### 3.7 开始游戏 StartGameRequest → StartGameResponse

**入参**：`room_id`、`player_id`

**逻辑**（全部在服务端校验，客户端按钮亮起只是表现层）：
1. 仅 `WAITING` 阶段允许
2. **仅 `owner_player_id` 可发起**，否则回 `FORBIDDEN`
3. **校验除房主外全员 `ready = true`（房主恒定视为已准备）**，未满足回 `BAD_REQUEST`（message 如 "有玩家未准备"）
4. 通过则 `phase = ROOM_PHASE_BATTLE`，`started_at_ms` 填当前时间
5. 返回 `StartGameResponse { status: OK, room }`
6. （第二批）推送 `RoomUpdated { room, reason: "game_started" }`；**未实现推送时，客户端轮询 GetRoom 发现 phase=BATTLE 后也会自动切入对局场景**

### 3.8 RoomUpdated 推送（第二批，推送是轮询的优化）

房间大厅状态每次变更向**房间全员**（含操作者本人）推送：

```protobuf
RoomUpdated {
  Room room = 1;     // 完整 Room
  string reason = 2; // player_joined / player_left / ready_changed / game_started
}
```

客户端收到后整体刷新 UI；`reason == "game_started"` 或 `phase ∈ {LOADING, BATTLE}` 时切入对局场景。

## 4. 局内同步接口（对局阶段）

### 4.1 状态上报 SyncPlayerStateRequest（最高频路径，30Hz/人）

**入参**：`room_id`、`player_id`、`transform: { position, direction, velocity, state_seq, client_time_ms, player_state, facing_left }`

**逻辑**：
1. 以 session 绑定的 player_id 定位玩家
2. 覆盖缓存 `players[player_id].transform = transform`，填 `server_time_ms`
3. **无需返回 SyncPlayerStateResponse**（客户端不处理）
4. 此路径要极快：不做校验、不写库，仅内存操作

`player_state`：`0=存活 1=幽灵（死亡） 2=已通关`，原样透传；`facing_left`：朝向，原样透传。

### 4.2 房间快照 RoomSnapshot（服务端推送）

**触发方式（二选一，建议先 A 后 B）**：
- **A. 立即广播**：每处理完一条 SyncPlayerState 就组装快照发给全房间（实现最简单）
- **B. 定时聚合**：每房间 15Hz 定时器，状态有变化（脏标记）才广播（省带宽）

**快照内容**：
```
RoomSnapshot {
  room_id, phase, tick（自增）, server_time_ms,
  players: [ 房间玩家表完整拷贝：{ player: {player_id, nickname}, hp, energy, score,
           connected, alive, ready, transform（含 player_state / facing_left，原样透传） } ]
}
```

- 通过 `ServerEnvelope.room_snapshot` 发给房间内每个 session（**包括上报者自己**，客户端自行跳过）
- 仅在 `BATTLE` 阶段需要广播

## 5. 连接维护

### 5.1 心跳 HeartbeatRequest → HeartbeatResponse

- 入参 `client_time_ms`；返回 `{ server_time_ms: 当前服务器毫秒, client_time_ms: 原样返回 }`
- 同时刷新 session 最后活跃时间

### 5.2 断线清理（P1）

- WebSocket 断开或超过 15s 无任何消息 → 该玩家处理：
  - **WAITING 阶段**：从房间玩家表移除（或标 `connected=false`）；若离开者是房主，解散房间或移交 owner 给剩余玩家第一位（建议先解散）
  - **BATTLE 阶段**：标 `connected=false`，触发一次 `RoomSnapshot` 广播，其他客户端据此移除/置灰该玩家化身
- 房间无人后延迟回收房间（如 60s）

## 6. 房间状态机

```
WAITING ──房主 StartGame 且全员 ready──→ BATTLE ──对局结束（客户端自行结算后离房）──→ CLOSED
```

- `WAITING`：可加入、可准备、可开局；客户端轮询 GetRoom 同步状态
- `BATTLE`：不可加入（回 BUSY）；广播 RoomSnapshot
- `LOADING` / `SETTLEMENT` 为预留枚举，当前版本可不使用

## 8. 联调验证清单

客户端 Console 过滤 `[NetWork]`，完整链路应依次出现：

**登录**：
```
连接已建立 → 点登录按钮弹窗输入账号密码 → 发送 LoginRequest
→ 收到 LoginResponse（拿到 player_id / nickname）→ 进入 Hall
错误密码 → LoginResponse UNAUTHORIZED → 弹窗红字"账号或密码错误"
```

**建房（房主）**：
```
发送 CreateRoomRequest（6位数字房间码）→ 收到 CreateRoomResponse
→ 发送 JoinRoomRequest → 收到 JoinRoomResponse → 进入 Room 场景
→ 显示房间码 + "开始游戏"按钮（灰，等全员准备）
```

**加房（好友）**：
```
发送 JoinRoomRequest（输入房间码）→ 收到 JoinRoomResponse → 进入 Room 场景
（房主端 2s 内轮询 GetRoom 看到新成员）
```

**准备与开局**：
```
好友点准备 → 发送 SetReadyRequest → 双方轮询同步到 ready 状态
→ 房主"开始游戏"按钮亮起 → 点击发送 StartGameRequest
→ phase=BATTLE → 双方切入 Level1 → 开始上报状态 → 首个房间快照到达
```

**双端各跑一次即可互见对方移动。**
